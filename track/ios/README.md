# Ozimut for iPhone and Apple Watch

One App Store app: the whole live site (https://ozimut.com) in a web view, plus what a web page cannot do — the live
GPS tracker that keeps sending with the phone locked, HealthKit routes, native notifications, files opened with the
app — and an Apple Watch app that tracks a run on its own. The contract with the server and the site is
[`docs/track/design.md`](../../docs/track/design.md); change it first, then this code.

## What is here

| Path | What |
|---|---|
| `project.yml` | The Xcode project, generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) (`xcodegen generate`). Never edit the `.xcodeproj` by hand: it is not in git. |
| `Shared/Core/` | The tracker's core, compiled into the iPhone app, the watch app and the tests: `TrackModels` (fixes, settings, pair codes, run ids), `BatchEncoder` (the `/api/track/push` body), `FixQueue` (the on-disk queue, plain SQLite), `TrackEngine` (batches, `ack`/`next`/`stop`, 401/409/413/429, retries 5 s doubling to 5 min, the network monitor, the cap, resuming a run), `TrackClient` (pair, claim, webtoken, pushtoken, push), `DeviceStore` (Keychain and preferences). |
| `Shared/UI/` | Texts (`L()`, the account's language, else the system's) and the hold-to-stop button. |
| `Shared/Activity/` | The Live Activity's attributes (app and widget). |
| `App/` | The iPhone app: `WebController` (the web view and the bridge), `AppModel` (state, bridge calls, pairing, files, push), `LocationTracker`, `HealthRoutes`, `LiveActivityController`, `WatchLink`, `Views/` (Start, Running, Ended, Pair with the QR scanner, the two-minute test). |
| `Widget/` | The Live Activity (lock screen and Dynamic Island): the run's clock, distance, positions waiting. |
| `Watch/` | The watchOS app (watchOS 10+, embedded in the iPhone app, also installable alone): claim code, pairing through the iPhone, `HKWorkoutSession` + location, Start / hold-to-Stop / Help. |
| `Tests/` | Unit tests of the batch encoder, the queue, the engine (against a fake server) and pair-code parsing. |
| `Resources/` | `Localizable.xcstrings` and `<lang>.lproj/InfoPlist.strings`, **written by `tools/strings.py`** (English base, French the reference wording, German « du », Spanish « tú »). Edit the tables there and run `python3 tools/strings.py`. |

Identifiers: `com.ozimut.app` (iPhone), `com.ozimut.app.watchkitapp` (watch), `com.ozimut.app.widget` (Live
Activity); URL scheme `ozimut`; universal links `https://ozimut.com/t/*`.

## Building

There is no Mac in the project: everything is built by GitHub Actions, `.github/workflows/track-ios.yml`, on every push
touching `track/ios/**` (any branch) and by hand (workflow_dispatch). It installs XcodeGen with brew, generates the
project, builds the iPhone app (with its widget and watch app) for the iOS simulator, the watch app alone for the
watchOS simulator, and runs the unit tests on an iPhone simulator — all with `CODE_SIGNING_ALLOWED=NO`. Compiler
errors appear as annotations on the run; the logs are kept as an artifact for a week.

On a Mac: `brew install xcodegen`, `cd track/ios && xcodegen generate`, open `Ozimut.xcodeproj`. A Debug build may point
at another server: change `OZ_BASE_URL` under `configs: Debug:` in `project.yml` (the base must end with `/`).

## What the owner must provide to publish

1. **Apple Developer Program** membership (99 USD a year), and the **team id** — set `DEVELOPMENT_TEAM` in
   `project.yml` (or pass it to xcodebuild).
2. In the developer account, the **App IDs** `com.ozimut.app` (capabilities: Associated Domains, Push Notifications,
   HealthKit), `com.ozimut.app.watchkitapp` (HealthKit) and `com.ozimut.app.widget`; an App Store Connect record for the
   app.
3. **Signing for CI**: a distribution certificate (.p12) and its password, and either the provisioning profiles of the
   three ids or an App Store Connect API key (`APP_STORE_CONNECT_KEY_ID`, `…_ISSUER_ID`, `…_KEY` .p8) for automatic
   signing. Suggested secret names: `APPLE_TEAM_ID`, `IOS_CERT_P12` (base64), `IOS_CERT_PASSWORD`,
   `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_KEY`. The workflow does not sign yet: a
   signed `archive` / `exportArchive` / upload job is to be added once they exist.
4. **Universal links**: the site must serve `https://ozimut.com/.well-known/apple-app-site-association` with
   `{"applinks": {"details": [{"appIDs": ["<TEAMID>.com.ozimut.app"], "components": [{"/": "/t/*"}]}]}}` (the
   server's side, not in this folder).
5. **Push (APNs)**: an APNs auth key (.p8), its key id and the team id, set as the Pages secrets `APNS_KEY`,
   `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_TOPIC` (= `com.ozimut.app`) — design.md « Native push tokens ». The app sends
   `env: "dev"` from Debug builds and `"prod"` from Release builds; the entitlement `aps-environment` is `development` in
   `project.yml` and becomes `production` when exported for the App Store.
6. The **app icon** is the Ozimut mark, `Resources/Assets.xcassets/AppIcon` (one 1024 px picture for the iPhone and the watch, no
   transparency), drawn by `track/tools/make_icons.py`.
7. HealthKit and location purpose strings are written; App Review will ask why the app tracks in the background:
   « live tracking of a run for the people the runner chose, only between Start and Stop ».

## Choices made

- **Location**: `CLLocationManager` with `allowsBackgroundLocationUpdates`, `pausesLocationUpdatesAutomatically =
  false`, no distance filter, `activityType = .fitness`, plus a `CLBackgroundActivitySession` held for the whole run
  (iOS 17). `CLLocationUpdate.liveUpdates(.fitness)` was not used: on iOS 17 it pauses while the phone is still
  (`isStationary`) and its cadence is the system's, while the contract asks one fix a second always. « When In Use »
  only; temporary full accuracy is asked when the user gave approximate location. No location outside a run, except the
  Start screen's single accuracy probe and the explicit two-minute test.
- **The queue**: SQLite through the system's libsqlite3 (no dependency), WAL; a fix is inserted on the engine's serial
  queue, the location callback returns at once. Batches are numbered when sealed and resent unchanged until
  acknowledged; a batch refused with 413 is cut in two and the later numbers move up.
- **Uploads**: ordinary `URLSession` requests (no background sessions), the timers of the engine's queue; they run in
  the background because the location updates keep the app alive.
- **Web view**: `WKAppBoundDomains` is *not* used. It would give the site its service worker inside the app, but it
  restricts every navigation and frame to the bound domains (Cloudflare Turnstile's frame on registration, a Debug base
  URL), and the site works without its service worker. The bridge only answers the site's own origins (ozimut.com,
  www.ozimut.com, ocn.kerkia.com, the configured base), in the main frame.
- **Pairing**: a code scanned, typed, opened as a universal link (`/t/<code>`) or `ozimut://…` pairs the phone and then
  signs the web view in with the pairing answer's `webToken` (`/t/login#<token>`); a pairing asked by the site through
  the bridge (`pair`) does not reload the web view (the page decides).
- **The watch through the iPhone**: the iPhone makes a pair code for its account through a session of that account
  (`webtoken` → `POST /api/track/session` in a cookie jar of its own → `POST /api/track/pair-code`), then sends it over
  WatchConnectivity; the watch calls `/api/track/pair` with kind `applewatch`. Without the iPhone the watch shows its
  claim code and asks `/api/track/claim` every 10 s.
- **The watch's recording**: an outdoor-run `HKWorkoutSession` keeps the app running wrist down; the route is written
  to HealthKit with the workout (`HKWorkoutRouteBuilder`).

## Not done yet

- Never run on a real iPhone or Apple Watch (no Mac, no signing): the background behaviour, the Live Activity, push and
  HealthKit are only compiled. The first signed build must be tried with the two-minute test, the phone locked.
- No signing, archive or TestFlight upload in CI (needs the owner's account and secrets above).
- No launch artwork (the system's plain launch screen).
- The watch does not take over a workout session the system ended (after a crash it starts a new one on relaunch).
- Gzip of the push body (accepted by the server, not needed at one batch every 30 s).
- The web view's language follows the site's own setting; the native screens follow the account's language.
